# 研究记录：FastAPI RAG 后端改造

## 目标

本文件用于沉淀本期架构上的关键取舍，避免后续实现时反复摇摆。范围围绕以下目标展开：

- 把 `D:\code\learning_rag` 从 CLI demo 改造成正式的 FastAPI 后端
- 对接 `E:\code\geminiBlog` 的 PostgreSQL `Post` 表作为文章真源
- 支持多轮会话、图文问答、上下文预算控制
- 首期直接使用 `LangGraph`
- 首期不引入 `mem0`
- 预留后续接入 Deep Agents 或其他 agent harness 的空间

## 结论摘要

### 1. 首期直接使用 `LangGraph`，不再把它当作“以后再说”的可选项

结论：

- 一期直接采用 `LangGraph` 作为问答编排与状态运行时。
- `LangGraph` 负责流程状态、节点编排、检查点恢复和中断/恢复语义。
- 不再以高层 `LangChain` chain 抽象作为项目主结构。

原因：

- 当前需求已经不是单次 `retrieve -> generate` 那么简单。
- 后续明确需要多轮会话、状态恢复、上下文裁剪、工具化扩展，`LangGraph` 更适合作为正式运行时。
- 如果先按简单单轮服务写死，后面再补多轮和 agent，会产生较大返工。

对实现的影响：

- 问答主链不再以一个 `ask()` 函数承载全部职责。
- 需要把“会话恢复、检索、图文合并、预算裁剪、生成、摘要更新”拆成显式节点或显式阶段。

## 2. 短期记忆与长期记忆必须分层

结论：

- 首期只做“会话级短期记忆 + 摘要记忆”。
- 长期记忆先预留扩展位，不作为一期强制交付。
- 记忆不能做成所有访客共享的一套全局内容。

分层方式：

- 共享层：博客知识库
  - 已发布文章
  - chunk
  - 图片 OCR
  - 图片说明
- 会话层：短期记忆
  - `session_id`
  - 最近多轮消息
  - 会话摘要
- 用户层：长期记忆
  - 首期不强上
  - 后续如需要，必须按 `user_id` 或稳定访客标识隔离

原因：

- 博客问答天然包含大量匿名访客。
- 如果不做会话隔离，多轮追问很容易串话。
- 如果把长期记忆提前做重，容易扩大复杂度和成本。

## 3. 首期不引入 `mem0`

结论：

- 一期不把 `mem0` 作为基础设施依赖。
- 会话消息、摘要记忆和可扩展记忆记录先由本项目自己的数据库结构承载。
- 后续如需要接入 `mem0`，通过独立适配层引入，不改对外 API。

原因：

- 当前真正必须解决的是：
  - 会话隔离
  - 多轮上下文恢复
  - 上下文预算控制
  - 图文 RAG 召回
- 这些问题首期可以通过：
  - `LangGraph` checkpoint / persistence
  - 自建 `chat_sessions / chat_messages / memory_records`
  - 摘要记忆
  来稳定解决。
- 如果此时再引入外部记忆中台，会增加一层新的边界、配置和运维成本。

保留的扩展策略：

- 记忆读写通过内部 `memory service` 暴露
- 后续若接 `mem0`：
  - 不改聊天 API
  - 不改 `session_id` 语义
  - 不改消息表主结构
  - 只在记忆服务后面加适配器

## 4. 文章真源必须是 PostgreSQL，而不是本地 Markdown 文件

结论：

- 生产数据源统一以 `E:\code\geminiBlog\prisma\schema.prisma` 中的 `Post` 表为准。
- 本仓库 `data/` 目录只保留为 demo 或测试材料，不作为正式问答真源。

原因：

- 用户已经明确当前博客的真实内容源在 PostgreSQL。
- `geminiBlog` 后台保存文章时也是先写数据库，再同步 GitHub。
- 如果 RAG 服务还继续盯本地文件，最终会出现三套源：
  - 数据库
  - GitHub 镜像
  - 本地 demo 文件
  这会让同步与排错非常混乱。

## 5. 图片策略：先做“图片文本化”，而不是先做图片向量

结论：

- 一期主策略是：
  - 提取 Markdown 图片
  - OCR
  - 生成图片说明
  - 结合邻近正文参与检索
- 不把独立图片向量检索作为一期必要能力。

原因：

- 你的图片很多是教程截图、操作指示图，这类图片最有价值的是：
  - 图片里的文字
  - 图片所在 section
  - 图片前后说明
- 首期做 OCR + caption 的性价比最高，也最容易进入现有文本 RAG 主链。

风险：

- OCR 原文过长，容易占用上下文预算
- 某些截图可能含大量无关界面文字

缓解：

- OCR 后先做清洗与摘要
- 对图片说明设置独立 token 上限
- 按相关性选择最多若干张图片进入最终上下文

## 6. 上下文预算必须是正式架构约束

结论：

- 上下文窗口不能靠“模型很大应该装得下”来赌。
- 首期必须把预算分配写成清晰策略，并配置化。

建议的一期预算思路：

- 系统提示：10% - 15%
- 会话最近消息：15% - 20%
- 会话摘要记忆：10% - 15%
- 检索文本 chunk：35% - 45%
- 图片 OCR / 图片说明：10% - 20%
- 预留输出空间：固定保留

核心原则：

- 检索命中不等于全部进入 prompt
- 历史消息不等于全部原样拼接
- OCR 原文通常优先进入摘要，而不是全文

需要的具体控制：

- `top_k` 控制
- chunk 最大长度
- OCR 最大长度
- caption 最大长度
- 最近消息轮数上限
- 摘要记忆长度上限

## 7. 检索策略：向量为主，图文合并，重排兜底

结论：

- 一期先采用：
  - 文本向量召回
  - 图片文本特征召回
  - 合并候选
  - reranker 重排

为什么不是先把 BM25 做成正式主方案：

- 当前文章量并不大
- 中文教程问法更容易从语义召回获益
- 图像相关文本并不天然适合传统关键词主导方案

保留项：

- 标题路径和章节路径继续保留
- 必要时可在后续补更强的关键词召回或混合检索
- 首版已接入父子 chunk 扩展窗口，在重排后围绕命中 chunk 补充前后相邻内容，减少教程步骤被截断的问题

## 8. 会话隔离规则必须是硬约束

结论：

- 所有访客不能共用同一套对话记忆。
- 共享的是知识库，不共享的是会话历史与记忆。

硬规则：

- 所有消息读写必须带 `session_id`
- 未来若有登录态，再附加 `user_id`
- `memory_records` 至少要有作用域字段
- 没有作用域的记忆内容不得参与用户问答

## 9. 对 Deep Agents 等 agent 框架的兼容策略

结论：

- 不在一期直接引入 Deep Agents
- 但必须为其保留边界

兼容原则：

- 数据层独立
- API 契约独立
- 会话层独立
- 记忆层独立
- 编排层通过 adapter 接入

换句话说，未来如果想把“问答图”升级成更复杂的 agent：

- 不应该要求重写数据库表
- 不应该要求重写博客端接口
- 不应该要求重写文档体系

## 10. 百炼模型建议

一期建议组合：

- 文本 embedding：`text-embedding-v4`
- reranker：`qwen3-rerank`
- OCR：`qwen-vl-ocr-latest`
- 图片说明：`qwen-vl-plus`
- 复杂图像兜底：`qwen3.6-plus`

注意事项：

- 当前实现通过百炼 OpenAI 兼容接口调用，默认地址为 `https://dashscope.aliyuncs.com/compatible-mode/v1`
- 博客中的 `/uploads/...` 图片地址需要通过 `BLOG_PUBLIC_BASE_URL` 拼成可访问地址后再进入 OCR / caption
- OCR 与 caption 需区分调用场景，不要把所有图都走重模型

## 未决问题

- `LangGraph` checkpoint 最终是否直接使用官方 Postgres 持久化，还是先走本项目自定义表加兼容封装
- 会话摘要是每轮更新，还是按消息数阈值批量更新
- 图片 caption 是否对所有图片都做，还是先按候选图片或启发式规则执行
- 父子 chunk 扩展窗口虽然已接入首版实现，但默认窗口大小、是否按 section 强约束、以及长文场景下的最佳上限仍需要继续调优

## 最终研究结论

本期最稳的方向是：

- `FastAPI + LangGraph + PostgreSQL + pgvector + 百炼`
- 会话隔离、多轮记忆、上下文预算作为一等能力
- 不把项目绑死在 `LangChain` chain 或外部记忆中台上
- `mem0` 暂缓
- Deep Agents 预留扩展位但不抢首期复杂度
