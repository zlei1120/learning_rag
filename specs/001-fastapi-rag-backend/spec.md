## 用户场景与测试

### 用户故事 1 - 同步博客文章并建立可检索知识库（优先级：P1）

作为维护者，我希望 RAG 后端可以从 `geminiBlog` 的 PostgreSQL 中读取已发布文章，完成 Markdown 解析、分块、向量化和索引更新，这样博客内容一更新，问答系统就能尽快使用最新知识。

**为什么是这个优先级**：没有稳定的数据同步和索引构建，就没有可用的问答能力，后续所有聊天与图片理解都无从谈起。

**独立测试方式**：向博客数据库插入、更新、隐藏一篇文章后，单独调用同步接口或异步任务，验证索引层是否只同步应同步的内容，并能在后台查询到对应 chunk、向量和图片关联记录。

**验收场景**：

1. **假如** 博客数据库中存在一篇 `published=true` 的 Markdown 文章，**当** 后端执行该文章的同步任务，**那么** 系统应生成文章记录、文本 chunk、向量数据以及图片关联信息。
2. **假如** 某篇文章正文内容发生修改，**当** 再次执行同步任务，**那么** 系统应仅更新受影响的 chunk、向量和图片解析结果，而不是强制全量重建全部文章。
3. **假如** 某篇文章被设置为 `published=false`，**当** 同步任务执行完成，**那么** 该文章不得再参与公开问答召回。

### 用户故事 2 - 在博客问答弹窗中基于文章内容回答用户问题（优先级：P1）

作为博客访客，我希望在博客页面的问答弹窗中提问，系统能够基于博主所有已发布文章内容给出准确回答，并返回来源文章与相关图片，这样我可以快速找到教程说明和上下文。

**为什么是这个优先级**：这是这个后端存在的核心价值，也是 `geminiBlog` 前端最终要消费的主要能力。

**独立测试方式**：在不依赖后台管理页面的情况下，直接调用问答 API，输入与文章内容相关的问题，验证回答、来源、相关图片和错误处理是否符合预期。

**验收场景**：

1. **假如** 用户提问内容可以在已发布文章中找到，**当** 问答接口返回结果，**那么** 响应中应包含回答正文、至少一个来源片段，以及可选的相关文章或图片引用。
2. **假如** 用户问题涉及教程截图中的文字或步骤，**当** 系统完成检索与生成，**那么** 回答应能够利用图片 OCR 或图片说明补足纯文本缺失的信息。
3. **假如** 用户提问与知识库无关，**当** 问答接口返回结果，**那么** 系统应明确说明当前资料无法支撑回答，而不是编造内容。

### 用户故事 3 - 支持多轮问答与会话记忆（优先级：P2）

作为博客访客，我希望问答不是只能单轮使用，而是能围绕同一个问题连续追问上下文，比如“上一张图里那个按钮在哪里”“你刚才说的第二步具体是什么”，这样我不用每次都把完整背景重新输入一遍。

**为什么是这个优先级**：虽然 demo 里还是单轮，但真实博客问答一旦上线，多轮跟进问题几乎是必然需求。如果现在的架构只按单轮设计，后面再补记忆和会话状态会返工很大。

**独立测试方式**：在同一个会话线程内连续发送两到三轮相关问题，验证系统是否能利用会话上下文理解指代、保持来源一致性，并在新开会话时正确隔离历史状态。

**验收场景**：

1. **假如** 用户在同一个会话中先问“这篇教程是怎么配置数据库的”，随后追问“第二步里的端口是什么意思”，**当** 第二轮问题到达后端，**那么** 系统应能结合前一轮上下文理解“第二步”所指对象。
2. **假如** 两个不同用户或两个不同会话线程提问相似问题，**当** 后端处理请求，**那么** 每个会话的历史上下文必须隔离，不能串话。
3. **假如** 某次对话需要跨多轮保留上下文，**当** 服务重启或异步恢复后继续处理，**那么** 系统应具备持久化会话状态的设计能力，而不是只依赖进程内内存。

**为什么是这个优先级**：后端接口即使做完，如果没有清晰文档，跨仓库接入成本会很高，容易在联调时反复返工。

**独立测试方式**：由不了解后端实现细节的开发者只依赖文档完成前端接入，能够成功发起问答请求、处理返回结构并展示来源与图片。

**验收场景**：

## 边界情况

- 博客文章存在大量图片但正文很少时，系统如何避免只靠稀疏正文导致召回失败。
- 文章更新后图片未变化，系统如何避免重复执行 OCR 与图片说明生成。
- 图片地址可访问，但 GitHub 私有资源代理失败时，系统如何区分“文本可答复”和“图片引用不可展示”两种状态。
- 某篇文章被删除、隐藏或修改 slug 后，旧索引、旧来源和旧图片关联如何清理。
- 数据库可读但 `pgvector` 扩展未安装时，系统如何暴露明确错误并阻止错误启动。
- 模型服务短暂失败、限流或超时时，问答接口如何返回可预期的错误结构。
- 前端连续发起高频提问时，系统如何限流并避免影响正常博客访问。
- 文档中包含代码块、表格、长列表、图片说明混排时，系统如何保持合理的 chunk 边界与标题上下文。
- 多轮会话中用户使用“这个”“刚才那个图”“上一段”这类指代表达时，系统如何利用会话状态正确解析。
- 同一用户的长期偏好、短期会话上下文和文章知识库内容混在一起时，系统如何避免记忆污染与跨会话串话。
- 当前直接采用 LangGraph 后，后续如果接入 Deep Agents 一类更高阶 agent harness，现有会话、记忆和检索数据结构如何复用，而不是被框架锁死。
- 单篇文章过长、命中图片过多、OCR 文本过长或多轮历史过深时，系统如何控制最终送入模型的上下文大小，避免超过上下文窗口或导致成本失控。
- 在上下文预算不足时，系统优先保留哪些内容，例如高相关 chunk、图片 OCR 摘要、最近轮会话消息、长期记忆摘要之间的取舍规则是什么。

## 需求

### 功能需求

- **FR-001**：系统必须将当前 `learning_rag` 改造成结构清晰的 FastAPI 项目，而不是继续以 CLI demo 作为主要运行方式。
- **FR-002**：系统必须以 `geminiBlog` 的 PostgreSQL `Post` 表作为文章正文真源，不再以本地 `data/` 目录文件作为正式生产数据源。
- **FR-003**：系统必须只索引 `published=true` 的博客文章，且公开问答不得召回未发布或已隐藏内容。
- **FR-004**：系统必须支持从文章正文中解析 Markdown 标题结构，并保留标题路径、章节信息、chunk 顺序等上下文元数据。
- **FR-005**：系统必须支持对博客文章执行增量同步，至少能够识别新增、更新、隐藏和删除四类变化。
- **FR-006**：系统必须为每个文本 chunk 生成文本向量，并将向量持久化到 PostgreSQL 中的 `pgvector` 存储结构。
- **FR-007**：系统必须使用百炼平台的文本 embedding 模型生成文本向量，当前默认模型为 `text-embedding-v4`。
- **FR-008**：系统必须使用百炼平台的 reranker 模型对候选结果重排，当前默认模型为 `qwen3-rerank`。
- **FR-009**：系统必须从文章 Markdown 中提取图片引用，并建立图片与文章、章节、chunk 的关联关系。
- **FR-010**：系统必须支持对重要图片执行 OCR 识别，当前默认模型为百炼的 `qwen-vl-ocr-latest` 或其兼容的最新稳定版本。
- **FR-011**：系统必须支持为图片生成可检索的简短说明或摘要，当前默认模型为百炼的 `qwen-vl-plus` 或其兼容的轻量视觉理解模型。
- **FR-012**：系统必须让图片 OCR 结果、图片说明和其邻近正文一起参与召回，而不是只把图片当作静态附件。
- **FR-013**：系统必须提供面向博客前端的问答接口，至少包括同步问答或流式问答能力，以及来源与相关图片返回结构。
- **FR-014**：问答接口返回结果时，必须包含回答正文、来源文章标识、来源片段，且在可用时返回相关图片引用。
- **FR-015**：系统必须在知识库无法支撑回答时给出明确拒答或降级提示，不得编造文章中不存在的事实。
- **FR-016**：系统必须提供内容同步相关接口或任务入口，至少支持按单篇文章同步、按 slug 重建、全量重建三类操作。
- **FR-017**：系统必须记录同步任务状态、失败原因、重试信息和关键时间点，便于后续运维和排错。
- **FR-018**：系统必须提供健康检查接口，用于博客端或部署环境确认服务可用状态。
- **FR-019**：系统必须提供结构化日志，覆盖启动、同步、检索、重排、模型调用、错误处理等关键阶段。
- **FR-020**：系统必须将现有 Markdown 分块能力迁移到服务化架构中，并保留适合教程文章的标题路径增强能力。
- **FR-021**：系统必须支持通过配置切换模型名、数据库连接、向量维度、重排开关、OCR 开关和图片说明开关。
- **FR-022**：系统必须与 `geminiBlog` 前端解耦，后端接口设计不能依赖浏览器本地状态或 CLI 交互。
- **FR-023**：系统必须提供详细的中文 API 文档，至少说明每个接口的用途、请求参数、响应结构、错误码、来源字段和图片字段。
- **FR-024**：系统必须提供详细的中文开发文档，至少说明目录结构、核心模块职责、环境变量、启动方式、同步流程、模型接入方式和常见故障排查。
- **FR-025**：系统必须提供详细的中文博客端接入文档，至少说明 `geminiBlog` 的 `chat-bot.tsx` 如何调用接口、如何处理流式返回、如何展示来源和图片、如何处理异常。
- **FR-026**：系统必须提供最小可运行示例或示例请求，方便前端与测试人员独立验证接口。
- **FR-027**：系统必须为核心能力补充自动化测试，至少覆盖同步流程、问答接口、图片解析链路和关键错误场景。
- **FR-028**：系统必须考虑云端 PostgreSQL 的正式运行场景，同时兼容本地 Docker 或开发环境调试。
- **FR-029**：系统必须避免在服务启动时自动清空向量数据或重建全部索引。
- **FR-030**：系统必须定义清晰的内部数据边界，使博客业务表与 RAG 索引表可以独立演进。
- **FR-031**：系统必须把多轮会话作为正式能力纳入设计，至少支持基于 `session_id` 或等价线程标识维护问答上下文。
- **FR-032**：系统必须支持短期会话记忆的持久化设计，不能把多轮上下文仅保存在单进程内存中。
- **FR-033**：系统必须预留长期记忆或用户记忆的扩展位，但首期可以只实现会话级记忆与摘要记忆。
- **FR-034**：系统必须直接使用 `LangGraph` 作为核心编排与状态运行时，承担多轮问答、检索编排、记忆恢复、上下文裁剪和可扩展的中断/恢复能力。
- **FR-035**：系统不得把核心架构建立在高层 `LangChain` chain 抽象之上；模型调用、检索、记忆、编排应以本项目的数据结构和服务接口为边界，由 `LangGraph` 负责流程状态编排。
- **FR-036**：系统必须为多轮问答接口定义清晰的会话字段、上下文恢复机制、历史消息裁剪策略，以及与 `LangGraph` checkpoint 或等价持久化机制的映射关系，并在 API 文档中明确说明。
- **FR-037**：系统必须把上下文预算控制作为正式能力设计，明确限制文本 chunk、图片 OCR、图片说明、会话历史和记忆摘要在单次生成中的总上下文占用。
- **FR-038**：系统必须支持在检索后按相关性和预算对候选内容进行裁剪、压缩或摘要，而不是简单把全部命中内容拼接进提示词。
- **FR-039**：系统必须支持多轮会话历史的裁剪与摘要策略，避免随着轮数增加导致上下文无限膨胀。
- **FR-040**：系统必须对图片 OCR 原文和图片说明设置独立的长度控制策略，必要时保留摘要而不是原始全文。
- **FR-041**：系统必须在开发文档和 API 文档中说明上下文窗口、预算分配、裁剪策略和可能对答案完整性造成的影响。
- **FR-042**：系统必须保留后续接入 Deep Agents 或其他 agent harness 的扩展位，但不应要求为此重写数据层、API 层、会话层和文档层。
- **FR-043**：一期实现不得引入 `mem0` 作为记忆基础设施，短期记忆、会话摘要和可扩展记忆记录应基于 `LangGraph` 与本项目自定义持久化结构完成。

### 关键实体

- **博客文章**：来自 `geminiBlog` PostgreSQL `Post` 表的正式内容对象，包含 `slug`、`title`、`content`、`published`、`tags`、`date`、`updatedAt` 等字段，是知识库的原始真源。
- **文章文档记录**：RAG 侧对单篇文章建立的索引主记录，用于追踪文章状态、内容哈希、最后同步时间和可见性。
- **文本分块**：从 Markdown 正文中切分出的可检索文本单元，携带 `title_path`、`section_id`、`chunk_index`、邻近上下文和内容哈希。
- **向量记录**：与文本分块一一对应的向量化结果，包含向量值、模型名称、向量维度和版本信息。
- **图片记录**：从文章中提取出的图片资源记录，包含图片 URL、原始 Markdown 引用、alt 文本、所在章节、OCR 文本、图片说明和状态信息。
- **图片文本特征**：由 OCR 和 caption 生成的可检索文本，用于增强图片教程内容的召回能力。
- **同步任务**：记录单篇或批量文章同步过程的任务实体，包含任务类型、目标文章、执行状态、错误信息、开始时间和完成时间。
- **会话线程**：一次连续问答的逻辑容器，至少包含 `session_id`、用户标识或匿名标识、创建时间、最近访问时间、状态摘要等字段。
- **会话消息**：会话中的单条用户或 AI 消息，至少包含角色、内容、时间、所属会话、引用来源和裁剪状态。
- **记忆记录**：从多轮会话中提炼出的短期摘要记忆或长期用户记忆，供后续多轮问答或未来 agent 扩展使用。
- **上下文预算**：单次问答请求可分配给系统提示、检索片段、图片文本、会话历史和记忆摘要的总上下文配额，用于控制成本、延迟和模型窗口占用。
- **问答会话请求**：面向博客前端的一次问答调用，包含用户问题、会话标识、可选上下文、返回答案、来源列表和相关图片列表。
- **接口文档资产**：用于博客端和维护者消费的说明材料，包含接口定义、字段说明、调用示例、错误处理和联调说明。

## 成功标准

### 可衡量结果

- **SC-001**：维护者可以在不修改本地文章文件的前提下，仅依赖 PostgreSQL 中的博客文章数据完成一次单篇同步和一次全量同步。
- **SC-002**：针对至少 24 篇现有博客文章，系统能够完成首轮索引构建，并且后续单篇更新时仅重建受影响文章的数据。
- **SC-003**：博客前端开发者可以仅凭 API 文档和接入文档，将 `chat-bot.tsx` 从 Mock 切换为真实接口调用，并成功展示回答、来源和图片。
- **SC-004**：对于涉及教程截图文字的测试问题，系统回答中有可验证比例的样例能够利用 OCR 或图片说明补足纯正文不足的信息。
- **SC-005**：当文章被隐藏或删除后，对应内容在下一轮同步完成后不再出现在公开问答结果中。
- **SC-006**：项目文档应覆盖本地启动、环境变量配置、数据库准备、模型配置、同步流程、API 调用、博客端接入和常见排错，且新维护者可据此完成首次运行。
- **SC-007**：系统在接口失败、模型超时、数据库异常和同步失败等场景下，能返回统一且可被前端识别的错误结构。
- **SC-008**：在同一会话内进行至少两轮追问时，系统能正确利用上一轮上下文完成回答；新会话不继承旧会话上下文。
- **SC-009**：项目的一期实现应直接基于 `LangGraph` 跑通多轮问答与状态编排，同时在不重写数据层和 API 层的前提下，为后续接入 Deep Agents 类 agent harness 保留清晰扩展边界。
- **SC-010**：在包含长文章、图片 OCR 和多轮历史的典型复杂问答场景下，系统仍能通过预算控制将送入模型的上下文保持在预设窗口内。

## 假设

- `geminiBlog` 的 PostgreSQL 连接信息可被当前后端安全访问，且允许为 RAG 功能新增表或新增 schema。
- 云端 PostgreSQL 可以安装并使用 `pgvector` 扩展；如线上环境有限制，需要在实施阶段尽早验证。
- 博客文章真源仍然是 PostgreSQL，GitHub 仓库继续作为文章镜像和图片存储/代理链路，而不是反向成为主要真源。
- `geminiBlog` 前端将继续使用 Next.js，并由现有的 `src/components/chat-bot.tsx` 承担问答入口。
- 图片公开展示继续沿用博客项目当前的图片代理方式，RAG 后端主要负责返回图片引用与语义信息，不直接承担前台图片托管职责。
- 本期优先实现“文本检索 + 图片 OCR/caption 增强召回”，暂不把独立图片向量检索作为第一阶段硬性范围。
- 百炼平台相关模型在本期可正常使用，且接口权限、配额与费用在实施前已被业务方接受。
- 本规格说明中的文档要求属于交付物本身，不是可选附加项；实现完成时必须同步交付。
- 本期直接以 `LangGraph` 作为核心编排层，但不以高层 `LangChain` chain 抽象作为项目主结构；如果后续引入 Deep Agents，也应复用当前的数据层、会话层和 API 契约，而不是反向推翻现有架构。
- 首期允许采用相对保守的上下文预算策略，优先保证稳定性和成本可控，再在后续版本逐步优化召回覆盖率与压缩质量。
- 本期暂不引入 `mem0`；如果未来需要接入外部记忆中台，再单独评估其与当前会话层、记忆层和 LangGraph 持久化状态的边界。
